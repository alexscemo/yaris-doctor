# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Android app for a Toyota Yaris diesel. It replaces the ESP32 dashboard in `../DPFViewer`. It runs as an always-on background service that connects to an ELM327 Bluetooth dongle and logs DPF soot, DPF temperature and the regen flag to SQLite. It records each regeneration with its duration and the GPS distance since the previous one, and shows an ongoing notification while a regen is running.

## Commands

There is no `gradlew`. A local toolchain lives in `C:\Users\alex\Android` (JDK 17, Gradle 8.11.1, SDK; `local.properties` points at it). In Git Bash, first `export JAVA_HOME="C:/Users/alex/Android/jdk-17.0.20.1+1"` and use `/c/Users/alex/Android/gradle-8.11.1/bin/gradle`:

- Emulator (AVDs `S25` / `S25_QPR`): see the `/emu` skill. adb from Git Bash needs `MSYS_NO_PATHCONV=1` and a Windows path for `install`.
- Install on the real phone: ask first.
- Logs: `adb logcat -s DpfService`
- Release: `/ship vX.Y.Z` (`.claude/skills/ship`). `.claude/settings.json` runs the unit tests after edits to the tested logic files and blocks touching the signing key.

CI (`.github/workflows/build.yml`) runs `gradle test assembleDebug` on every push and PR. It pins Gradle via `setup-gradle` because there is no wrapper jar.

**Release:** `git tag vX.Y.Z && git push origin vX.Y.Z` builds a signed APK and publishes it as a GitHub Release, which Obtainium on the phone installs. `versionName` comes from the tag, `versionCode` from the run number. The signing key (`~/.android-keys/yaris-doctor.p12` + `.password.txt`, alias `yaris`) lives outside the repo. It is stored in the repo secrets `KEYSTORE_BASE64` / `KEYSTORE_PASSWORD`. Never regenerate it: a different key forces an uninstall, which wipes the phone's database.

## Architecture

- **No AndroidX or third-party dependencies.** It uses only framework APIs: `android.app.Activity`, `Notification.Builder`, `SQLiteOpenHelper`, `LocationManager`, and plain `Thread`. JUnit is the only dependency, for tests. minSdk 31, so Android 12+ Bluetooth permissions only.
- **UI:** cool paper canvas (near-black at night), one signal orange (`primary`, black text on it), heavy Hanken Grotesk numerals, PT Mono uppercase labels, dark instrument card. The brand's full stop is `Ui.SquareSpan`, a square after the hero word or number (orange, or the status colour on the health verdict). Fonts are bundled in `res/font` (OFL licences in `licenses/fonts`); weights come from font variation settings. `DESIGN.md` (local, gitignored) still describes the older cream/coral look. Screens are built in code, with no layout XML. `Ui.kt` holds the type scale (`Ui.Type`) and the few components (cards, pills, circular icon button, top bar). Colours are resource tokens in `res/values/colors.xml`, with dark-mode overrides of the same names in `res/values-night/colors.xml`: never hard-code hex in Kotlin. `res/values(-night)/themes.xml` (`AppTheme`, no action bar) styles the status bar, switches and dialogs. `MainActivity` refreshes every 5 s while visible. `ChartView` is a hand-drawn Canvas chart (line on a time axis, or columns by index): the series is coral, which DESIGN.md allows for line-art on cream. It falls below 3:1 contrast on the light card, so the always-visible readout row must stay. A line chart can shade time ranges behind the data (`chart_band`, a faint orange, at least 3dp wide so an 11-min regen shows on a 14-day axis): the Overview soot trend and the All data last-trip chart shade the regens from `Db.regens()`, an open one up to now. Column charts don't. 
- **`DpfService`** is a foreground service (`connectedDevice|location`), started by `MainActivity` after permissions are granted and by `BootReceiver` on boot or app update. One worker thread loops:
  - **Idle:** sets an `AlarmManager` `ELAPSED_REALTIME_WAKEUP` alarm every `PROBE_MS`, wakes on a `Semaphore`, and tries an RFCOMM SPP connect to the dongle picked in Settings (`Prefs.dongle`, defaulting to the DPFViewer MAC). The phone has to start the connection because the dongle never connects on its own. The alarm exists because CPU sleep freezes `Thread.sleep`.
  - **Connected:** holds a non-reference-counted wakelock, starts GPS and runs `Poller.cycle()` back to back with no pause, so the pace is whatever the dongle and ECU manage, the same in and out of a regen. Each cycle stores every reply as a `frame` row and takes soot / temp / regen from the replies to the three DPF codes. The `sample` row keeps its old pace (5 s, 1 s in regen; a regen start or end is written at once).
  - **Ignition off:** the dongle may stay powered, so ECU silence counts as ignition off. The session ends after 1 dead cycle if no data was ever seen (a quick probe), or after 3 dead cycles mid-drive. A dead cycle mid-drive re-runs `elm.init()`, which unwedges some clones.
  - **Regen interrupted by disconnect:** the `finally` block cancels the notification but leaves the regen open. `rec` lives on the service, so a link back within `REGEN_GAP_MS` (2 min) continues the same regen; otherwise `run()` closes it at `rec.lastT`.
  - **Process killed mid-regen:** no `finally` runs, so the row stays open. `onCreate()` calls `Db.closeOrphanRegens()`, which ends each open regen at its last regen sample before the next regen, the same rule as the hub's `close_if_stale`.
- **Full live-data table:** `PidTable.kt` is GENERATED by `tools/pid_table.py` from the Techstream sheet (`../techstream/NLP130_engine_PIDs.xlsx`): 102 items over 35 `21 <lid>` requests. Never hand-edit it. `Pid.decode()` is Techstream's ValueConvert (MSB-first bit fields, two's complement, integer `raw*mul/div + offset`, then `/10^decimals`). `min`/`max` are display ranges only: some signed items have min 0 and still go negative.
- **`Poller`** decides what each cycle asks: `FAST` codes every cycle, two `MEDIUM` codes in turn, one `SLOW` code when not read for 5 min. One request returns a block holding many values (102 values over 35 requests). On the owner's dongle a request takes ~140 ms, so a cycle of ~13 requests takes ~2 s. Order matters for values compared across requests: the service passes its DPF codes with `21DD` (rail target) last, and `FAST` starts with `2123` (actual rail pressure). Coolant and MAP are `MEDIUM` because they change slowly. Error handling:
  - A reply counts only with the exact length from the table, the `61<lid>` header and hex only; otherwise it is retried once.
  - Single-frame requests get the ELM response-count suffix (`210C1`). After 3 suffix failures that the plain retry fixed, the suffix is dropped for the session.
  - A code missing `PARK_AFTER` times in a row while others answer is parked for the session.
  - A cycle stops after 3 misses with nothing answered (ignition off would otherwise wait out every timeout).
  - Codes outside the table (a user's own DPF codes) pass through unchecked.
  - **Ash record** (`Poller.ASH_RECORD`, `A9 18`, in `SLOW`): the ECU's DPF ash estimate, what Techstream calls "DPF Deterioration Record". It is the same read as Techstream's Learning Values Confirmation (J2534 log, 21 Oct). The reply is `E9 18` + 13 bytes, the last being the XOR of the other 12 (`ashRecordOk()`). The format is undocumented, so it's stored raw as frame lid `A918`. The Overview's DPF card shows the newest read, grouped like Techstream. Techstream's Vehicle Mileage Write sets it with `3B 18 01 <km/10>`, and Record Clear sends `3B 18 00 00`. The app never writes it.
  `PollerTest` checks that FAST + MEDIUM + SLOW cover the table exactly.
  Values a rule compares with each other must be read in the same cycle, so they belong in FAST. Example: `212C` / `21EA`, the EGR target and actual position compared by `egr_tracking`. MEDIUM codes are read in different cycles, seconds apart.
- **Tabs:** `MainActivity` has two chips under the top bar (`Ui.chip`). "Overview" is the original screen. "All data" is `AllData`: every `PIDS` item, filtered by category chip (categories come from the generator's keyword list) and by name search, showing the latest value per lid via `Db.latestFrames()`. Each row shows how often it updates, measured from its own frames in the last trip (`Db.readEvery()`). Tapping a row opens a chart of the last trip (`Db.tripStart()`: the newest `0C` frame with none in the `TRIP_GAP_MS` before it). `ChartView` zooms the x axis with a pinch, pans with two fingers and resets on double-tap. Only the visible tab refreshes. `PID_IDLE` (also generated) holds the captured idle payloads. They are test fixtures, and `Sim.frames()` patches the simulated soot, temps, regen, rpm, speed and coolant into them so Debug mode fills the tab.
- **Health checks** (`Checks.kt`, tested in `ChecksTest`) run on the phone; the hub will only display them.
  - **Live checks:** `Checker` is one per drive. The service feeds it each cycle's replies, and it returns `Finding`s.
    - Every rule has a hold time, so one odd reading never fires.
    - Values older than 6 min are ignored.
    - The coolant-rise rule keeps 2 min of history. A "soot rising fast" rule existed and was removed: on the owner's car it fired every drive; `regen_frequent` says the same once per regen.
    - **`regen_flag_check`:** Toyota's own regen sign is After Injection Period (`21AD`, MEDIUM) above 0. The rule warns when it and the app's regen flag disagree for 5 min with the engine running. After injection counts as on for 90 s after its last non-zero read, because mid-regen it drops to 0 for up to 55 s on the owner's car (overrun, idle) and `21AD` is read every ~18 s. On the 21 Oct log the two never disagreed; a build with the wrong regen byte (11) would have fired 5 min into the 09:33 regen. Short NOx purges also after-inject but last seconds. `Sim.frames()` sets it during simulated regens.
  - **Model year:** `Prefs.model2015` (Settings → Car → Model year, "2011-2014" default, the owner's car). `Checker(model2015)` takes the soot levels from `sootLimits()` (needed / P2463: 100 / 150 %, 2015+: 118 / 174 %), `trends()` the B1S2 regen maximum from `regenTempMax()` (700 / 750 °C) and the All data tab the `TOYOTA_NORMAL_2015` lines through `toyotaNormal()`. The service reads it once at start, so a change restarts it. Rule descriptions name both years, so the hub's copy (`ruleDefs()`) stays static.
  - **History checks:** `DpfService.history()` = `trends()` on the regen history (interval under 150 km, last 3 regens under 10 min) plus `sensorZero()`: the DPF pressure with the engine stopped and ignition on (`Db.engineOffDp()`) must be within -0.5..1 kPa (the owner's reads 0.3-0.4), plus `oilDue()`. Recomputed at start, when a regen closes and when a drive ends.
    - **Regen warning signs:** `Db.withSigns()` adds each regen's `floor` (first soot sample 5-10 min after it ended, own or peer; null when no phone was connected) and `peakTemp` (max sample `temp`, i.e. B1S2, during it), computed at read time with no schema change. It costs a few indexed queries per regen, so callers pass only the regens they use (the last 10 for `history()`, the last 50 for the Overview list). `trends()` judges the newest finished regen that has each value, so a drive that ended before the floor could be read doesn't clear the warning.
    - **`soot_floor`:** floor of 30 % or more (estimate). A burn ends near 10 %; Toyota's 2011-2014 DPF test passes a filter at 40 % or less after two forced regens. The owner's car read 38-40 % at +5 min (and 10 % at the end of the burn) while its ash record was cleared, with regens every ~40 km.
    - **`regen_hot`:** peak over 700 °C (2015+: 750), the top of Toyota's B1S2 regen range. The owner's regens peak at 627-638 °C.
    - **Oil:** Settings → Car → Oil changed stores `Prefs.OIL_AT` (time) and `OIL_ODO` (the real log's GPS odometer, metres) and restarts the service. `Prefs.oilMetres()` = odometer now minus `OIL_ODO`, this phone's GPS only. The row shows distance and regens since. `oil_change_due` warns from 15000 km (Toyota's interval, checked in the P252F procedure); never when no change was recorded.
  - **DPF condition:** `restriction()` = DPF pressure per 100 l/s of exhaust (MAF turned into volume at the after-DPF temperature, ~1 atm; null under 1200 rpm or 25 l/s). `Db.dpfConditions()` gives, per finished regen, the median restriction in the 5 min after it (`base`, what burning can't remove: ash) and its rise per km until the next regen (`perKm`). The window is 5 min because the owner's filter already rises a lot within 15. Shown on the Overview ("DPF condition" card) and sent to the hub. On 21 Oct: base 6.7, +0.14 per km. Under it, the ECU ash record (`A918`) with `Db.ashHistory()`: its readings where the value changed (`LAG` over the `A918` frames), newest first, last 10.
  - **Trip summary:** when a drive ends (ECU silent for `REGEN_GAP_MS`), `tripDone()` posts one low-importance "Drive finished" notification from `Db.tripStats()`: distance, soot first → last, regens and warnings started.
  - **Rules tab:** every `Checker.Rule` carries a `title`, an `about` (condition, threshold, source) and `uses` (the `PIDS` names it reads). The **Rules** tab (`RulesTab`, third chip on the main screen) lists them with their hold time and each input's poll rate from `Poller.pollRate()`; `TREND_RULES` describes the `trends()` checks. A new rule must fill all three, and `ChecksTest` fails if a `uses` name isn't in the table.
  - **Thresholds:** each rule's `about` names its source. "Estimate" marks the ones taken from other Toyota diesels or generic OBD logic, because no 1ND-TV figure was found. Tighten them once real drives show the normal range.
  - **Toyota repair manual:** where the 1ND-TV manual (Yaris RM, read 21 Oct, notes in `../techstream/RM_NOTES.md`) gives a figure, the rule uses it and its `about` says so. Before a threshold was tightened, the owner's 21 Oct logs were checked against it so it doesn't fire on a healthy car.
    - The page versions used are the 2011-2014 ones, matching the owner's Nov 2013 car. Soot: regen may start above 77 %, needed at 100 %, P2463 over 149 %. 2015+ cars use 105/118/173 %.
    - The EGR closed learned value's 0.7 V lower limit is left out: the owner's car reads 0.48 and Toyota's own test car 0.52.
    - `TOYOTA_NORMAL` (`Normal.kt`) holds the manual's normal value per `PIDS` name. All data shows it under each value; `ChecksTest` checks that every name exists.
  - **Alerts:** `Db.syncAlerts()` (table `alert`, schema v5) keeps one open row per active key. It closes the row when the key goes away and returns newly opened keys. The service notifies each of those on the low-importance "Health warnings" channel. When the value recovers, the row is closed (kept as history and synced) and its notification cancelled. Each key notifies at most once per drive (`notified`), so a value flapping around its limit doesn't spam; `showing` tracks which notifications are still up.
  - **`diffAlerts()`:** the open/close/update decision is a pure function in `Checks.kt`, tested in `ChecksTest`. `Db.syncAlerts()` only applies it.
  - **When alerts close:** a drive outlives a Bluetooth drop, like a regen does. `checker`, `notified` and the open live alerts live on the service. `run()` resets them, and closes the live alerts, once the ECU has been silent (`lastSeen`) for more than `REGEN_GAP_MS`. So a flaky dongle neither re-notifies a warning nor splits its row. Regen-history alerts stay open while they apply.
  - **Overview:** the status card at the top shows "All good", "Warning" or "Check the car now", with the open alerts only. Recovered ones leave the dashboard.
- **Motion:**
  - **All data:** values that changed since the last refresh fade from `flash_up` (green tint) or `flash_down` (red tint) over 1.2 s.
  - **Overview:** the instrument card's background is a `SootView`: `soot_fill` rises from the bottom to the soot %. A change animates the level and, for 4 s, shows specks settling when soot went up, or coral embers lifting when it went down.
  - **Reduced motion:** with system animations off, the level jumps and no particles are drawn. The view only redraws while something moves.
  - **Contrast:** `on_instrument_soft` keeps 4.5:1 on `soot_fill`, so text stays readable at any level.
- **`frame` table** (schema v4): `t`, `lid`, `hex` = the payload after `61 <lid>`, decoded on read. `DpfService.thin()` keeps one frame per lid per minute for data older than 30 days. Each stretch is thinned once, tracked by `Prefs.THINNED_TO`.
- **`Recorder`** turns readings into `sample`/`regen` rows (regen open/close transitions). It is shared by the real session, Debug mode and the fake history, so there is one copy of the regen logic.
- **Settings** live in `Prefs` (SharedPreferences) and are edited in `SettingsActivity`. Changes the service must see (dongle, logging, Debug mode, model year, oil change) go through `DpfService.restart()`, which stops the service so a fresh instance re-reads them. `DpfService.start()` is the only start path (activity, boot) and respects the logging toggle and the Bluetooth permission. Settings → Your data → Export database writes a `VACUUM INTO` snapshot of `yaris.db` (never Debug data) to Downloads through MediaStore, which needs no storage permission.
- **Overview regen list:** each row shows duration, soot start → end, then the soot 5 min after (`floor`) and the peak DPF temperature from `Db.withSigns()`. The list also rebuilds once the newest regen's floor window has passed.
- **Debug mode** (`Prefs.debug`) is a process-lifetime flag, deliberately never persisted. While it is on, `Db.get()` returns an in-memory `Db` (name `null`) seeded by `Sim.seed()` with 14 days of history, and `DpfService.simulate()` feeds `Sim.live()` readings instead of opening Bluetooth. `yaris.db` is never touched. Turning it off calls `Db.dropDebug()`.
- **`Elm.kt`** ports ELMduino's response handling so the DPFViewer char offsets still apply. `parse()` keeps only `[A-Za-z0-9:.\r]`, returns null on `NODATA`/`UNABLETOCONNECT`/`STOPPED`/`ERROR`, and joins multi-frame (`N:`) replies, trimmed to the byte count on the first line. Decoders index the hex string by **character** (2 per byte). `init()` mirrors `myELM.begin(..., '6')` plus `AT SH 7E0` / `AT CRA 7E8` and `AT AT2` (adaptive timing).
- **Distance / "odometer":** the car's odometer PID is unknown, so distance comes from GPS fixes, counted only while a session is connected. Fixes with accuracy over 25 m or speed under 1 m/s are dropped. `odoM` is written only by the GPS callback on the main thread and read by the worker (`@Volatile`). It persists as `sample.odo_m`, and the service restores it at start from `MAX(odo_m)`, so there is no separate prefs store.
- **`Db`** is a per-process instance (`Db.get`), shared by the service and the activity. Tables `sample` and `regen`. Distance between regens is computed at read time in `regens()` in metres (`gapM`); the UI converts to miles or km per `Prefs.km`. It is this regen's `odo_start` minus the previous regen's `odo_end`. Schema version is 5: v2 added the `sample(t)` index the charts' range queries rely on, v3 the peer tables, v4 `frame`, v5 `alert`. Every schema change needs a step in `onUpgrade`, or it will wipe users' history.

## Regen notification = Android 16 Live Update (Now Bar on Samsung, status chip elsewhere)

- On API 36+, `DpfService.liveUpdate()` sets the `android.requestPromotedOngoing` extra (what `setRequestPromotedOngoing()` does; that method only exists from API 36.1, so it can't be called with compileSdk 36), a coral `ProgressStyle` (share of the starting soot burned off, from `burnPercent()`) and `setShortCriticalText("<soot>%")` for the chip. One UI 8 shows promoted notifications in the Now Bar. Keep the rules or promotion is silently dropped: ongoing, a content title, a non-MIN channel, never `setColorized(true)`, no custom views. The `POST_PROMOTED_NOTIFICATIONS` permission is in the manifest. Settings shows `canPostPromotedNotifications()` and links to the system toggle, falling back to the app's notification settings when a manufacturer lacks that screen. Nothing here is Samsung-only: no Samsung SDK, just the Android 16 API, and the brand is only used for wording.
- That needs compileSdk 36 (AGP 8.10.1). targetSdk is still 35 on purpose: raising it changes Android 16 behaviour (edge-to-edge, predictive back) and needs on-phone checks.

## Edge light

`EdgeLight` adds a full-screen `TYPE_APPLICATION_OVERLAY` view (a blurred coral stroke along the screen outline, its corners taken from `Display.getRoundedCorner()`, square where the display reports none) while a regen runs and `Prefs.edge` is on. It needs `SYSTEM_ALERT_WINDOW`, which is opt-in from Settings. The window is `FLAG_NOT_TOUCHABLE` with `alpha = 0.8f`: Android 12+ blocks touches through untrusted overlays above 0.8 opacity, so raising it would freeze Google Maps. Window calls are posted to the main thread because `publish()` runs on the worker.

## Home hub sync

- The server is a separate public repo, [yaris-doctor-hub](https://github.com/alexscemo/yaris-doctor-hub) (image `ghcr.io/alexscemo/yaris-doctor-hub`). Its `/api/sync` payload shape must stay in step with `Sync.kt` + `Db.samplesAfter()` / `Db.regenRows()`.
- `Sync.maybe()` is called once a minute from the service's idle loop. It uploads only when `Prefs.server` and `Prefs.wifi` are both set (both empty by default) and the current SSID matches. SSID comes from `Sync.watch()`'s NetworkCallback with `FLAG_INCLUDE_LOCATION_INFO`, which needs fine + background location. It uploads when there are new samples (by SQLite `rowid`) or the regen signature changed, and waits 15 min after a failure. It always reads `Db.real()`, so Debug data never leaves the phone. `usesCleartextTraffic` is on because hubs are plain-http LAN servers.
- **Two-way:** after uploading, `Sync.run()` pages through the hub's `GET /api/export?device=<own id>&after=<cursor>` (cursor `Prefs.PULLED_ROWID`, the hub's sample rowid). It stores the other phones' rows in `peer_sample` / `peer_regen` (schema v3) through `Db.putPeers()`, ignoring re-sent samples and replacing the whole peer regen list. `Sync.maybe()` also pulls every 10 min on the home Wi-Fi when there is nothing to send. Changing the hub address resets both cursors.
- **The main screen shows the whole car:**
  - `lastSample`, `sootSeries`, `regens` and `metresSinceRegen` read own and peer rows together.
  - Car distance between two instants is `driven()`: the sum of each phone's odometer progress, as in the hub's `distance_m`.
  - `mergeRegens()` (tested in `SyncTest`) counts a hand-over burn once, but never merges open regens.
  - `odometer()` stays own-only, because the service restores its GPS odometer from it.
- **Regens and DPF condition:** the first sync request carries `regens_all: true` with the phone's whole regen list, and the hub deletes that phone's regens missing from it (engine-stop blips the phone dropped). It also carries `dpf` (`Db.dpfRows()`), which the hub stores whole per phone and charts. The hub's status card shows open alerts only, like the Overview.
- **Frames, alerts and the PID table:** the first sync request also carries `alerts` (`Db.alertRows()`, open plus the last 30 days, resent whole when `alertSignature()` changes) and `defs` (`pidDefs()`, which the hub decodes frames with, so the formulas live only in `PidTable.kt`). Frames follow in pages of `BATCH`, at most `MAX_PAGES` per run, with cursor `Prefs.SYNCED_FRAME_ROWID`. The hub only accepts 2-character lids, so `framesAfter()` and `maxFrameRowid()` both skip the `A918` ash record rows. With only one of the two filtered, a sync would be rejected or would look pending forever.
  - **Hubs from before frames:** they drop these fields silently. They are detected by the missing `frames` key in the sync reply and stored in `Prefs.HUB_FRAMES`. The frame cursor then doesn't move, and frames/alerts don't count as pending, so the phone doesn't sync every minute; the 10-minute pull rechecks.
  - **Hub side:** the hub keeps every frame. It serves `/api/live` and `/api/series`, and its dashboard has a Live data view and the same status card as the Overview.
  - **Rule descriptions:** the first request also carries `rules` (`ruleDefs()`: key, title, level, description and value names for every `Checker.RULES` and `TREND_RULES`). The hub's warning detail shows them, with a chart of each value around the warning.
  - **All warnings:** a hub that never got this phone's warnings (`SYNCED_ALERTS` unset: first sync, or a new address) gets all of them. After that, the last 30 days.
  - **"All synced" notification:** the automatic sync (`Sync.maybe` → `run(c, notify = true)`) posts one low-importance "All synced with the hub" notification when it uploaded readings, frames or changed warnings. "Sync now" in Settings shows a toast instead.
  - **Phone side:** phones don't download other phones' frames or alerts.
- `hubUrl()` normalises what the user types ("192.168.1.50" → `http://192.168.1.50:8765`); it is unit-tested in `SyncTest`.
- versionCode is `run_number + 2000`, which keeps it above the retired private `-home` builds (1000+). Never lower the offset.

## Facts from the car (do not change without on-car confirmation)

- The three requests (`21DD` soot, `21F1` temperature, `21DF` regen) are defaults in `Prefs.PID_DEFAULTS`. Users can change them in Settings → DPF codes for other Yaris years; `pidCode()` only lets 2–4 hex bytes starting with a read service (`21`, `22`, `01`) through, so no `AT` command or ECU-changing service (reset, actuators, writes) reaches the car. Byte positions and formulas are configurable the same way:
  - Positions: `Prefs.byte()`, defaults in `Prefs.BYTE_DEFAULTS`, checked by `bytePos()`.
  - Formulas: `Prefs.formula()`, defaults in `Prefs.FORMULA_DEFAULTS`, checked by `formulaText()`.
  - `Formula` in `Elm.kt` is a small Torque-style parser:
    - `A`–`D` are bytes from the position on.
    - Operators are `+ - * /`, `&` (lowest precedence) and brackets.
    - It evaluates to null past the reply's end or when the result isn't finite.
  - Results are truncated to Int. The regen flag is on when its formula gives exactly 1.

  The session reads codes, positions and formulas once at connect, so a change restarts the service.
- Defaults (byte 0 = the echoed `61`):
  - soot: byte 19, `A*2` (%)
  - DPF temp: byte 8, `(A*256+B)*0.625` (°C)
  - regen: byte 16, `A&15`, on when it is 1 (DPFViewer's char 33). Confirmed on the car: the 21 Oct drive's regen (09:33-09:44, DPF ~600 °C, soot 90 → 10) had it on throughout while byte 11 stayed 0. The ECU also sets it as the engine stops with the ignition on (first seen at 346 rpm spinning down, then 0), so `engineStopped()` ignores it below `RUNNING_RPM` (500; idle is ~770) on the `210C` reply. `Db.dropStopBlips()` deletes closed regens under a minute with no distance, at every service start and whenever a regen closes, so a blip that slips through never counts in `trends()`.

  Soot and temp are DPFViewer's char offsets 38 and 16; the temp is Exhaust Temperature B1S2. The Techstream capture (`../techstream/NLP130_RUNTIME_RESULTS.md`) confirmed both.

  The Techstream sheet names that bit "VN Turbo Operation Prohibit", and byte 11 is "DPNR/DPF Status Reju(PM)". A build that switched the default to byte 11 `A-1` on that label never fired on the road: the capture had no regen in it, so it could not show which bit moves. `Prefs.migrate()` moves installs that saved 11 / `A-1` back. Never change a car fact from a sheet label alone; it needs a frame log of the event itself.

  `ElmTest.decodersUseDpfViewerOffsets` pins the defaults.
