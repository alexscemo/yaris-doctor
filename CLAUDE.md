# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Android app for a Toyota Yaris diesel. It replaces the ESP32 dashboard in `../DPFViewer`. It runs as an always-on background service that connects to an ELM327 Bluetooth dongle and logs DPF soot, DPF temperature and the regen flag to SQLite. It records each regeneration with its duration and the car's distance (its own odometer) since the previous one, and shows an ongoing notification while a regen is running.

## Commands

The repo has a Gradle wrapper pinned to 8.11.1, and CI uses it. A local toolchain lives in `C:\Users\alex\Android` (JDK 17, Gradle 8.11.1, SDK; `local.properties` points at it). In Git Bash, first `export JAVA_HOME="C:/Users/alex/Android/jdk-17.0.20.1+1"` and use `./gradlew` (or `/c/Users/alex/Android/gradle-8.11.1/bin/gradle` if the wrapper jar is missing):

- Unit tests + lint + debug APK: `./gradlew -q test lint assembleDebug`, then `./gradlew --stop` to free memory. `lint` is part of CI and fails the build on errors.
- Single test: `./gradlew :domain:test --tests "com.yarisdoctor.domain.car.DecodersTest.decodersUseDpfViewerOffsets"` (an `:app` test: `./gradlew :app:testDebugUnitTest --tests "com.yarisdoctor.ElmTest.*"`)
- Emulator (AVDs `S25` / `S25_QPR`): see the `/emu` skill. adb from Git Bash needs `MSYS_NO_PATHCONV=1` and a Windows path for `install`.
- Install on the real phone: ask first.
- Logs: `adb logcat -s DpfService`
- Release: `/ship vX.Y.Z` (`.claude/skills/ship`). `.claude/settings.json` runs the unit tests after edits to the tested logic files and blocks touching the signing key.

CI (`.github/workflows/build.yml`) runs `./gradlew test lint assembleDebug` on every push and PR, through the committed wrapper.

**Release:** add a `## [X.Y.Z] - date` section to `CHANGELOG.md` first (its text becomes the GitHub release notes, and a tag without a section fails the release step), then `git tag vX.Y.Z && git push origin vX.Y.Z` builds a signed APK and publishes it as a GitHub Release, which Obtainium on the phone installs. A tag with a hyphen (`v1.0.0-rc.1`) is published as a pre-release, which Obtainium only installs with "Include prereleases" on. `versionName` comes from the tag, `versionCode` from the run number. The signing key (`~/.android-keys/yaris-doctor.p12` + `.password.txt`, alias `yaris`) lives outside the repo. It is stored in the repo secrets `KEYSTORE_BASE64` / `KEYSTORE_PASSWORD`. Never regenerate it: a different key forces an uninstall, which wipes the phone's database. versionCode is `run_number + 2000`, which keeps it above the retired private `-home` builds (1000+). Never lower the offset.

## Architecture

- **Modules (clean architecture):** `:domain` is plain Kotlin with no Android on its classpath, so the build rejects an `android.*` or `org.json` import there. It holds the car logic: `domain.car` (`Pid`, the generated `PidTable.kt`, `Normal.kt`, the DPF decoders in `Decoders.kt`), `domain.health` (`Checks.kt`), `domain.drive` (`DriveSession`, `Poller`, `Recorder`, `Sim` with its `seed()`, `mergeRegens` and `burnPercent` in `Regens.kt`), `domain.repo` (`RegenLog`, the three writes `Recorder` makes, and `DriveStore`, what a drive reads and writes besides; `Db` implements both, tests use fakes) and `domain.model` (`Regen`, `Sample`, `Alert`, `TripStats`, `Units`/`UnitSystem` and the shared time and distance constants). `domain.export` (`AiExport`) writes the AI-ready Markdown, fed by `AiExportDb.kt` in `:app`. `:app` keeps everything Android: `Db`, `Prefs`, `Elm` (the ELM327 link and `parse()`), `Sync` with the hub payload tables (`HubDefs.kt`: `ruleDefs()`, `pidDefs()`), the service and the screens.
- **Dependencies:** AndroidX Activity and Lifecycle only (`ComponentActivity`, `ViewModel`, `lifecycleScope`, which bring Kotlin coroutines), for the screens; no AppCompat, Room or DI library. Everything else is framework APIs: `Notification.Builder`, `SQLiteOpenHelper`, and a plain `Thread` in the service (its dongle I/O is blocking and the alarm is what survives CPU sleep). `:domain` has no dependencies; JUnit is the only test dependency. minSdk 31, so Android 12+ Bluetooth permissions only.
- **UI:** cool paper canvas (near-black at night), one signal orange (`primary`, black text on it), heavy Hanken Grotesk numerals, PT Mono uppercase labels, dark instrument card. The brand's full stop is `Ui.SquareSpan`, a square after the hero word or number (orange, or the status colour on the health verdict). Fonts are bundled in `res/font` (OFL licences in `licenses/fonts`); weights come from font variation settings. `DESIGN.md` (local, gitignored) still describes the older cream/coral look. Screens are built in code, with no layout XML. `Ui.kt` holds the type scale (`Ui.Type`) and the few components (cards, pills, circular icon button, top bar). Colours are resource tokens in `res/values/colors.xml`, with dark-mode overrides of the same names in `res/values-night/colors.xml`: never hard-code hex in Kotlin. `res/values(-night)/themes.xml` (`AppTheme`, no action bar) styles the status bar, switches and dialogs. `MainActivity` redraws on every live reading the service pushes (`Live`, one per poll cycle, so about every 1-2 s) and on a 5 s fallback tick for what a reading can't carry (the wall clock, other phones' rows, a stopped service), while visible: `OverviewViewModel.load()` reads everything on `Dispatchers.IO` and keeps the costly parts (the DPF condition card, the regen list's floor and peak) until their key changes, and `render()` draws it; the charts redraw only when their cached series changes. `Live` is in-memory only: nothing is stored or synced, and `load()`, `render()` and `AllData` all take the reading from it when it is newer than the log's last `sample`. `AllData` reads its rows the same way. No database read runs on the main thread. The tile row under the instrument shows DPF temperature, distance since the regen, the regen state and **Next regen** (`forecast()` in `:domain`, unit-tested): the soot rise since the last finished regen projected onto the level this car's regens start at, or "drive a little more" when there is no trustworthy trend. `ChartView` is a hand-drawn Canvas chart (line on a time axis, or columns by index): the series is coral, which DESIGN.md allows for line-art on cream. It falls below 3:1 contrast on the light card, so the always-visible readout row must stay. A line chart can shade time ranges behind the data (`chart_band`, a faint orange, at least 3dp wide so an 11-min regen shows on a 14-day axis): the Overview soot trend and the All data last-trip chart shade the regens from `Db.regens()`, an open one up to now. Column charts don't. 
- **`DpfService`** is a foreground service (`connectedDevice` only: no GPS; the location permission is kept just for the Wi-Fi name, see hub-sync), started by `MainActivity` after permissions are granted and by `BootReceiver` on boot or app update. The drive logic below lives in `DriveSession` (`:domain`, tested in `DriveSessionTest` with a scripted `ObdLink` and a fake clock); the service keeps the Android side (Bluetooth socket, wakelock, alarm, notifications and edge light, through `DriveEffects`). One worker thread loops:
  - **Idle:** sets an `AlarmManager` `ELAPSED_REALTIME_WAKEUP` alarm every `PROBE_MS`, wakes on a `Semaphore`, and tries an RFCOMM SPP connect to the dongle picked in Settings (`Prefs.dongle`, defaulting to the DPFViewer MAC). The phone has to start the connection because the dongle never connects on its own. The alarm exists because CPU sleep freezes `Thread.sleep`. **Plugged in** (`ACTION_POWER_CONNECTED`) also wakes it at once: `CarPowerReceiver` (manifest, `exported=false`) starts the service when it isn't running, and `DpfService` registers the same action at runtime because Android 16 sends it as a registered-only broadcast. That is what closes the "first minutes of a drive aren't logged" gap for people who plug the phone in. **The car's Bluetooth** (Settings → Car's Bluetooth, `Prefs.carBt`, the head unit; the dongle is left out of the picker) does the same for everyone else: `CarBtReceiver` gets `ACL_CONNECTED` / `ACL_DISCONNECTED` (exempt broadcasts, sent under the Bluetooth stack's uid, so the receiver is exported behind `BLUETOOTH_CONNECT`), starts and probes the service even at home, and keeps `Prefs.CAR_BT_ON` while connected (reset at boot). `session()` picks the link from the bonded device's type: classic or dual/unknown connects with the SPP service record and, only if that fails, retries once through the hidden `createRfcommSocket(1)` channel that some clones need; BLE-only, or dual/unknown when SPP failed, goes through `BleLink` (GATT by address, no scan: the first service with a notify and a write characteristic, known ELM327 serial services first, exposed as the same two streams `Elm` reads). The Vgate iCar Pro 2S shows up as two devices: "Android-Vlink" (classic, PIN 1234) and "IOS-Vlink" (BLE); a socket that connects and then stays silent is a normal ignition-off end, never a retry.
  - **Connected:** holds a non-reference-counted wakelock and runs `Poller.cycle()` back to back with no pause, so the pace is whatever the dongle and ECU manage, the same in and out of a regen. Each cycle stores every reply as a `frame` row and takes soot / temp / regen from the replies to the three DPF codes. The `sample` row keeps its old pace (5 s, 1 s in regen; a regen start or end is written at once), while the screens get the same reading every cycle through `DriveEffects.live` → `Live`: a fast screen costs the log nothing.
  - **Ignition off:** the dongle may stay powered, so ECU silence counts as ignition off. The session ends after 1 dead cycle if no data was ever seen (a quick probe), or after 3 dead cycles mid-drive. A dead cycle mid-drive re-runs `elm.init()`, which unwedges some clones.
  - **Regen interrupted by disconnect:** the `finally` block cancels the notification but leaves the regen open. The `DriveSession` (and its `Recorder`) lives as long as the service, so a link back within `REGEN_GAP_MS` (2 min) continues the same regen; otherwise `DriveSession.idle()` closes it at `rec.lastT`.
  - **Process killed mid-regen:** no `finally` runs, so the row stays open. `onCreate()` calls `Db.closeOrphanRegens()`, which ends each open regen at its last regen sample before the next regen, the same rule as the hub's `close_if_stale`.
  - **Paused at home:** on the home Wi-Fi (`Prefs.wifi`, the hub setting) the idle loop stops the service (no dongle search, no notification) once `pauseAtHome()` holds: not Debug mode, no drive or regen still open (`DriveSession.busy`), nothing the hub hasn't confirmed (`Sync.pending()`; a paused service doesn't sync), no sync queued or running, the car's Bluetooth not connected (`Prefs.carBtOn`), and the app exempt from battery optimisation. That exemption is what lets `HomeWatch` (an `setAndAllowWhileIdle` alarm about once a minute, checking the SSID with a one-shot `FLAG_INCLUDE_LOCATION_INFO` callback) start the foreground service again from the background when the phone is off that Wi-Fi; without it the service keeps running. `onCreate()` cancels the watch. Opening the app at home starts the service, which syncs and pauses again. `Sync.unwatch()` clears `Sync.ssid`, or a restarted service away from home would read a stale "home" and pause again at once. A drive that starts while still on the home Wi-Fi is logged from about a minute after the Wi-Fi drops (`setAndAllowWhileIdle` can stretch that while the phone idles), unless the car's Bluetooth is set: then it is logged from the ignition.
  - **Hub sync:** runs on its own single-thread executor (`dpf-sync`), never on the worker, so a long upload cannot delay the next dongle probe; `syncQueued` keeps it single-flight and `onDestroy` shuts it down. `Sync.run()` is time-boxed (`SYNC_BUDGET_MS`, 120 s) and stops between pages with every cursor already persisted, so the next run continues; `SYNCED_REGENS` is written only once the first batch actually reached the hub.
- **Full live-data table:** `PidTable.kt` (`:domain`, `domain.car`) is GENERATED by `tools/pid_table.py` from a vehicle PID sheet (`NLP130_engine_PIDs.xlsx`): 102 items over 35 `21 <lid>` requests. Never hand-edit it. `Pid.decode()` follows the sheet's value conversion (MSB-first bit fields, two's complement, integer `raw*mul/div + offset`, then `/10^decimals`). `min`/`max` are display ranges only: some signed items have min 0 and still go negative.
- **`Poller`** decides what each cycle asks: `FAST` codes every cycle, two `MEDIUM` codes in turn, one `SLOW` code when not read for 5 min. One request returns a block holding many values (102 values over 35 requests). On the owner's dongle a request takes ~140 ms, so a cycle of ~13 requests takes ~2 s. Order matters for values compared across requests: `FAST` starts with the three DPF codes, `21DD` (soot and rail target) last of them, then `2123` (actual rail pressure). Coolant and MAP are `MEDIUM` because they change slowly. Error handling:
  - A reply counts only with the exact length from the table, the `61<lid>` header and hex only; otherwise it is retried once.
  - Every request gets the ELM response-count suffix (`210C1`), so the ELM returns on the reply instead of waiting out its timeout. A genuine ELM counts a multi-frame reply as one; a clone may cut it short. Single-frame (7 bytes or less) and multi-frame requests fall back separately: after 3 suffix failures of a kind that the plain retry fixed, the suffix is dropped for that kind for the session.
  - A code missing `PARK_AFTER` times in a row while others answer is parked for the session.
  - A cycle stops after 3 misses with nothing answered (ignition off would otherwise wait out every timeout).
  - **Ash record** (`Poller.ASH_RECORD`, `A9 18`, read every `ASH_MS` = 1 min): stored raw as frame lid `A918`. The **calibration ID** (`Poller.CAL_ID`, `09 04`) is no longer asked; a row older builds stored under lid `0904` is still kept and exported. Format, decoding, the owner's DPF history and the write commands are in `.claude/rules/ash-record.md`. The app never writes the record.
  `PollerTest` checks that FAST + MEDIUM + SLOW cover the table exactly.
  Values a rule compares with each other must be read in the same cycle, so they belong in FAST. Example: `212C` / `21EA`, the EGR target and actual position compared by `egr_tracking`. MEDIUM codes are read in different cycles, seconds apart.
- **Tabs:** `MainActivity` has a bottom navigation bar (`NavItem`: icon over label, the open tab's icon in an orange pill; icons `res/drawable/ic_tab_*.xml`): Overview, Data, Maintenance, Rules, daily first. Each tab keeps its scroll position, tapping the open tab scrolls it to the top, and Back goes to Overview before it leaves the app. "Overview" is the original screen. "Data" is `AllData`: every `PIDS` item, filtered by category chip (categories come from the generator's keyword list) and by name search, showing the latest value per lid via `Db.latestFrames()`. Each row shows how often it updates, measured from its own frames in the last trip (`Db.readEvery()`). Tapping a row opens a chart of the last trip (`Db.tripStart()`: the newest `0C` frame with none in the `TRIP_GAP_MS` before it). `ChartView` zooms the x axis with a pinch, pans with two fingers and resets on double-tap. Only the visible tab refreshes. `PID_IDLE` (also generated) holds the captured idle payloads. They are test fixtures, and `Sim.frames()` patches the simulated soot, temps, regen, rpm, speed and coolant into them so Debug mode fills the tab.
- **Maintenance tab** (`MaintenanceTab`, logic in `domain.maintenance`, tested in `MaintenanceTest`): the car's mileage, "Coming up" and the logbook, always `container.real` (Debug mode included). A `maintenance` row (`Job`) is done or planned, has a `day` (epoch day, so months use `plusMonths`), optional `km` (the car's odometer), `odo_m` (the logged odometer, set when a done row is written on its own day) and a `every_km` / `every_months` reminder. Mileage (`carKm()`): once the cluster has been read (`Db.lastClusterRead()`), the logged odometer itself; before that, the newest done row with both `km` and `odo_m` (`anchor()`; "Set mileage", shown only until the first cluster read, writes a `MILEAGE` row) plus the distance logged since, clamped at 0. Distance since a row is `odo_m` when it has it, else the mileage minus its `km`. `upcoming()`: each planned row, plus the newest done row per kind ("Other" per note) when it set an interval; a planned row replaces its kind's interval. Overdue rows become one `maintenance_due` warning (`maintenanceDue()`, metric text without separators so `Units.text()` converts it) through `DriveSession`'s history checks. Inputs are whole numbers in the display unit, stored in km. It loads per visit and after each change, never on the live tick, and every change calls `DpfService.restart()` so the warning updates at once. Only oil has a default interval (`OIL_CHANGE_KM`). The logbook is not synced to the hub nor in the AI export.
- **Health checks** (`Checks.kt`, tested in `ChecksTest`) run on the phone; the hub will only display them. Details (rules, thresholds, alerts, DPF condition, Rules tab) are in `.claude/rules/health-checks.md`, which loads with the files it covers.
- **Motion:**
  - **All data:** values that changed since the last refresh fade from `flash_up` (green tint) or `flash_down` (red tint) over 1.2 s.
  - **Overview:** the instrument card's background is a `SootView`: `soot_fill` rises from the bottom to the soot %. A change animates the level and, for 4 s, shows specks settling when soot went up, or coral embers lifting when it went down.
  - **Reduced motion:** with system animations off, the level jumps and no particles are drawn. The view only redraws while something moves.
  - **Contrast:** `on_instrument_soft` keeps 4.5:1 on `soot_fill`, so text stays readable at any level.
- **`frame` table** (schema v4): `t`, `lid`, `hex` = the payload after `61 <lid>`, decoded on read. `DpfService.thin()` calls `Db.thinFrames(now)`: full resolution for 7 days, one row per lid per minute from 7 to 90 days, one per lid per hour after that, keeping the newest row of each bucket. With a hub set, nothing from the oldest frame the hub hasn't received is thinned (the hub keeps every frame). Progress is in `Prefs.THINNED_TO` and `Prefs.THINNED_HOURLY_TO`, and the call is idempotent, so nothing is thinned twice. A full-rate month (the old 30-day window) grew to roughly 100-150 MB for a normal driver, and the first hub sync had to upload all of it.
- **`Recorder`** turns readings into `sample`/`regen` rows (regen open/close transitions), written through `RegenLog`. It is shared by the real session, Debug mode and the fake history, so there is one copy of the regen logic. `RecorderTest` covers it against an in-memory `RegenLog`.
- **Settings** live in `Prefs` (SharedPreferences) and are edited in `SettingsActivity`. Changes the service must see (dongle, logging, Debug mode, model year; the Maintenance tab too) go through `DpfService.restart()`, which stops the service so a fresh instance re-reads them. `DpfService.start()` is the only start path (activity, boot) and respects the logging toggle and the Bluetooth permission.
  - **Export database** writes the whole real log (never Debug data) to Downloads through MediaStore, which needs no storage permission. It is one Markdown file an AI can read: front matter, a legend, a summary, then trips, regenerations, warnings, every reading (other phones' readings too), per-trip engine-signal statistics, dongle timings, the ash record and the calibration ID. `AiExport` (`:domain`) owns the format and is unit-tested; `AiExportDb.kt` streams the rows from SQLite, so a long log never has to fit in memory. Raw frames are decoded into per-trip statistics rather than copied (they stay in the database and on the hub).
  - **Back up / Restore database** are the restorable pair, separate from the Markdown export. `DatabaseBackup.export()` writes a consistent SQLite snapshot to Downloads with `VACUUM INTO` (`yaris-doctor-backup-YYYYMMDD-HHmm.db`); `restore()` checks the picked file's 16-byte SQLite header, schema version and tables, then replaces every table (the `maintenance` logbook included) in one transaction (a failure leaves the log alone) and calls `Db.invalidatePeers()`. `SettingsActivity` resets the sync cursors after a restore so the next sync re-uploads the restored rows. `DatabaseBackupTest` runs the round trip on Robolectric. Android's own cloud backup excludes the database (`res/xml/data_extraction_rules.xml`) because it outgrows the 25 MB quota and used to fail silently; device-to-device transfer still includes it. `AppDialog` sets `android:windowBackground` (`res/drawable/dialog_bg.xml`), or the dialog's text floats over the screen.
  - **Delete trips** lists this phone's trips (`container.real.trips()`, never Debug data). A trip is a run of `sample` rows with no gap over `TRIP_GAP_MS`; its rows are those in `Trip.start..Trip.until`, which is the last sample + `TRIP_GAP_MS`. That window catches the frames and warnings written just after the last sample and never reaches the next trip. The trip in progress can't be picked. **Delete** (red) shows what will go (`tripCounts()`) behind a `HoldButton`, which has to be held 1.5 s. It is timed by the clock, not an animator, so it still holds with animations off; TalkBack's long press confirms. `deleteTrips()` removes this phone's rows only, and a warning still open stays. Deleting the newest trip winds the logged odometer back, so `oilMetres()` is clamped at 0.
- **Quick Settings tile** (`SootTile`): soot % and whether a regen is burning, read when the shade opens (`Live` if newer than `lastSample()`, like the Overview); a tap opens the app.
- **Overview regen list:** each row shows duration, soot start → end, then the soot 5 min after (`floor`) and the peak DPF temperature from `Db.withSigns()`. The list also rebuilds once the newest regen's floor window has passed.
- **Debug mode** (`Prefs.debug`) is a process-lifetime flag, deliberately never persisted. While it is on, `container.db()` returns an in-memory `Db` (name `null`) seeded by `Sim.seed()` with 14 days of history, and `DpfService.simulate()` feeds `Sim.live()` readings instead of opening Bluetooth. `yaris.db` is never touched. Turning it off calls `container.dropDebug()`.
- **Dongle link timing:** `Elm` reads the Bluetooth stream on its own thread (`elm-rx`) into a queue, so `send()` wakes the moment a byte arrives. Polling `available()` with 10 ms sleeps used to add up to 10 ms per burst. Per command it sums `Elm.Timing`:
  - the time from send to the first byte;
  - the tail, from the last data byte to the `>` prompt, i.e. the ELM waiting for more;
  - the total.
  At session end `Db.linkStats()` writes the averages to table `link` (one row per command per session; AT commands left out). All data's header shows the last session's average (`Db.linkAverage()`). It's there to compare dongles and settings from exports; nothing is synced.
- **`Elm.kt`** ports ELMduino's response handling so the DPFViewer char offsets still apply. `parse()` keeps only `[A-Za-z0-9:.\r]`, returns null on `NODATA`/`UNABLETOCONNECT`/`STOPPED`/`ERROR`, and joins multi-frame (`N:`) replies, trimmed to the byte count on the first line. Decoders index the hex string by **character** (2 per byte). `init()` mirrors `myELM.begin(..., '6')` plus `AT SH 7E0` / `AT CRA 7E8` and `AT AT2` (adaptive timing).
- **Meter ECU (`Meter`, `:domain`, tested in `MeterTest`):** between engine cycles, outside regens, `DriveSession` reads the instrument cluster (`AT SH 7C0` / `AT CRA 7C8`, then back to 7E0/7E8, a full `init()` if that fails) when the service passes `MeterHooks`; tests and Debug mode don't. **Fuel level:** `21 29` every `FUEL_MS` (1 min), stored raw as frame lid `M29` (never synced), shown as the Overview's Fuel tile at byte × 0.5 L per Techstream's database. Confirmed on the car 29 Oct 2026 (6.5 L before a 34.7 L fill-up, 39 L after; a full tank reads flat at ~39 L, and it swings ~3.5 L while driving); three misses stop it for the session. **Odometer probe:** a one-shot armed by the Settings toggle (`Prefs.ODO_PROBE`, cleared once it ran): `21 28`, `21 ED`, `01 A0`, `01 A6` on the engine, `21 02`, `21 E2` on the meter, then `Elm.monitor()` (`AT MA` with `AT H1`) for 20 s on CAN id 0x611 and 5 s unfiltered. The answers go to frame lids `ODO:…` with `ODO:KM` (the logbook mileage then) and to the export's "Odometer probe" section. Why: Techstream has no odometer read for this car (techstream repo, `RM_NOTES.md`, 28 Oct 2026).
- **Fill-ups** (`fuel` table, `Fill` and `spending()` in `domain.maintenance`, `FuelTest`): the Maintenance tab's Fuel section (this month, this year, average price per litre, the last 10) and the Overview's Fuel tile (a tap opens the add dialog). Money is integer cents in the phone's currency; litres and price accept `,` or `.`. Not synced, not in the AI export. A fill-up's `odo_m` is the car's odometer at the stop where the meter saw the tank rise (`Db.fillOdometer()`: `refills()` finds rises of `MIN_REFILL_L` or more across an engine-off pause in the `M29` reads, `matchRefill()` picks that day's nearest in litres), because owners log it after driving on; without a seen rise it falls back to the odometer at saving, for today only. Saving an older line again re-runs the match, which corrects one logged before this.
- **Distance / odometer:** `odo_m` everywhere (`sample`, `regen`, `frame`, `alert`, `fuel`, `maintenance`) is the car's own odometer in metres. No GPS. `DriveSession.odoM` follows it: `Meter.odometer()` listens on the cluster's 0x611 broadcast (`Meter.ODO_LISTEN_MS`, ~1.5 s) on the first cycle of a drive and every `Meter.ODO_MS` (5 min), outside regens, three misses stopping it for the session; `Odometer.snap()` keeps the figure inside the whole mile the dash shows (the middle of it on a drive's first read when it was outside); in between, `Odometer.advance()` adds the `210D` vehicle speed cycle by cycle (nothing across a gap over 10 s). Each read is a row in table `odometer` (t, miles, odo_m) through `DriveStore.odometerRead()`. The **first read ever** (`Db.firstRead()`) moves every row so far by the step it took, from the old GPS figures (or speed since a fresh install) onto the car's, and resets the sync cursors so the hub gets everything again; rows before `Db.odoRealFrom()` are estimates, and the AI export says so per row (`odometer_source`). The v9 upgrade did that at once from the probe's `ODO:611` frame (29 Oct 2026, 89,159 mi), shifting the owner's history to 88,812–89,159 mi. Frames written before v9 get theirs from the sample timeline in `Db.fillFrameOdo()` (chunks of 20,000 rows on the worker after a session, `Prefs.ODO_FILLED_TO` / `ODO_FILLED`), since the upgrade itself runs on the main thread. The service starts `odoM` from `Db.odometer()` (`MAX(odo_m)`).
- **Units:** `Prefs.units()` (`domain.model.Units`, key `Prefs.KM` for compatibility) is the one switch: imperial shows mi, °F, psi, mph and lb/min, metric km, °C, kPa, km/h and g/s. The ECU, database, hub payload, AI export and stored alert texts stay metric; `Pid.format(v, units)`, `Units.text(metricText)` (rule descriptions) and the numeric converters in `MainActivity`/`DpfService` convert only at the display edge. The Rules tab is rebuilt per visit so its prose follows a change made in Settings.
- **`Db`** is created only by `AppContainer`, which `YarisApp` (the manifest's `Application`) owns, so the service, the activities and the boot receiver share one per process. Code reaches it through the `Context.container` extension: `container.db()` (the Debug database while Debug mode is on) or `container.real` (always `yaris.db`). Tables `sample` and `regen`. Distance between regens is computed at read time in `regens()` in metres (`gapM`); the UI converts with `Prefs.units()`. It is this regen's `odo_start` minus the previous regen's `odo_end`, computed set-based: one `TEMP TABLE odo_at` of boundary instants and one indexed statement per phone, instead of two queries per phone per regen (the Overview refreshes every 5 s). After `mergeRegens()` it applies `mergeSameBurn()`, so a burn split by the ignition is one row with one gap; the raw `regen` table and `regenRows()` (the hub payload) keep both rows. `invalidatePeers()` drops the cached phone list after `DatabaseBackup.restore()` rewrites the peer tables. Schema version is 9: v2 added the `sample(t)` index the charts' range queries rely on, v3 the peer tables, v4 `frame`, v5 `alert`, v6 `link`, v7 `maintenance` (and moves the oil change older builds kept in `Prefs.OIL_AT` / `OIL_ODO` into it), v8 `fuel`, v9 the car's odometer (`odometer` table, `odo_m` on `frame`, `odo_start` / `odo_end` on `alert`, the history moved onto the car's odometer). Every schema change needs a step in `onUpgrade`, or it will wipe users' history.

## Facts from the car (do not change without on-car confirmation)

- The three DPF requests are fixed: `PID_SOOT` `21DD`, `PID_TEMP` `21F1`, `PID_REGEN` `21DF` (`Decoders.kt` in `:domain`). Settings once let users change the codes, byte positions and formulas for other Yaris years; nobody used it, so it was removed along with its formula parser.
- Decoders `sootOf()` / `tempOf()` / `regenOf()` (byte 0 = the echoed `61`; results truncated to Int like DPFViewer's casts):
  - soot: byte 19 × 2 (%)
  - DPF temp: bytes 8-9 × 0.625 (°C)
  - regen: byte 16, on when its low nibble is 1 (DPFViewer's char 33). Confirmed on the car: the 21 Oct drive's regen (09:33-09:44, DPF ~600 °C, soot 90 → 10) had it on throughout while byte 11 stayed 0. The ECU also sets it as the engine stops with the ignition on (first seen at 346 rpm spinning down, then 0), so `engineStopped()` ignores it below `RUNNING_RPM` (500; idle is ~770) on the `210C` reply; a set bit in a cycle without a `210C` reply leaves the regen state as it was (ignition off mid-cycle answers `21DF` but not `210C`: 22 Oct, 17:53). `Db.dropStopBlips()` deletes closed regens under a minute with no distance, at every service start and whenever a regen closes (also through `idle()`), so a blip that slips through never counts in `trends()`.

  Soot and temp are DPFViewer's char offsets 38 and 16; the temp is Exhaust Temperature B1S2. Live captures on the car confirmed both.

  The PID sheet names a bit of that byte "VN Turbo Operation Prohibit", and byte 11 is "DPNR/DPF Status Reju(PM)". A build that switched the regen flag to byte 11 on that label never fired on the road: the capture had no regen in it, so it could not show which bit moves. Never change a car fact from a sheet label alone; it needs a frame log of the event itself.

  `DecodersTest.decodersUseDpfViewerOffsets` (`:domain`) pins the defaults.
- **Odometer:** the cluster broadcasts it on CAN id 0x611, about once a second: `611 21 00 00 04 00 01 5C 47`, the first data byte `21`, the odometer in the last 3 bytes, big endian, in **whole miles** (UK cluster). Confirmed by the 29 Oct 2026 probe: 0x015C47 = 89,159 mi = 143,487.5 km, the dash reading the owner entered. Byte 3 (`04`) may be a unit flag; unconfirmed. The engine ECU answers none of `21 28`, `21 ED`, `01 A0`, `01 A6`, and the meter refuses `21 02` (`7F 21 12`). `MeterTest` / `Meter.odoMiles()` pin the layout.
- Dongle MAC `66:1E:32:7A:2E:72`, PIN `1234`. It must be paired in Android settings first.
